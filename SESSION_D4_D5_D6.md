## Starting point

D1–D3 (retrieval, text-to-query) were complete and measured. D4 (grounded
narrative generation) had been built in an earlier session but had a real
architectural fault: Track B was computing the price waterfall itself by
summing graph records, which is Track A's job, not Track B's. That was fixed
first — the waterfall now arrives pre-computed in Track A's payload, and
`scripts/build_sample_payload.py` (which simulates Track A, since her real
engine doesn't exist yet) was moved outside `src/` to make that boundary
visible in the file layout.

The task for this session: finish D4's English requirements, build D5
(reliability layer: k=3 self-consistency, abstain-on-disagreement, corrective
retrieval, hallucination checks), and build D6 (evaluation harness with
faithfulness/relevance/coverage metrics and a measured served-wrong rate),
explicitly deferring Arabic.

## Part 1 — Finishing D4

The acceptance criterion says *"every narrative claim cites a specific
record"*. The existing verifier checked that cited records were **valid**,
not that every claim **carried** one — a narrative could state twelve figures
across four sentences and pass with a single citation at the end.

Added citation-coverage counting to `verify()`
(`NARRATIVE_MIN_CITATION_COVERAGE`, default 1.0: every sentence stating a
figure must cite the record it rests on).

**Enforcing it broke the system**, which is what measurement is for: service
rate dropped to 58%, with zero first-attempt passes. The fix was to the
**prompt**, not the threshold — a worked example of the required citation
density, with synthetic figures verified absent from the real data so the
model can't be caught copying them. Service went to 100%, all first-attempt.

## Part 2 — Building D5

Three mechanisms, in `src/reliability/`:

**`attribution.py`** — catches a number that is correctly attested but
attached to the wrong noun: *"the invoice price is ⟨list price's value⟩"*
passes D4's verifier cleanly (the figure is real, the citation resolves) and
is still false. This module was rewritten **four times** during this session
because each version, when run against real generated text rather than
hand-written test strings, produced a false positive on correct prose. Each
is recorded in Part 4 below — that's the part of this log worth reading if
you only read one section.

**`consistency.py`** — k=3 sampling with abstain-on-disagreement. Measuring
before implementing changed the design: three samples of one fact pack, at
temperature 0.7, gave 7, 11 and 9 distinct figures with **identical citations
and no contradiction anywhere**. A naive set-equality or Jaccard disagreement
test would have called that a disagreement and abstained on every healthy
run, because the samples differ in *how much* they say, not *what* they say.
Agreement is instead measured on the consensus core — figures a majority of
samples state — as a fraction of everything anyone states.

**`corrective.py`** — re-retrieves supporting records when evidence is thin.
Two defects found by running it against the real graph, not by inspection:

1. It admitted whatever retrieval ranked highest, which for an explanation of
   order line `OL000001` meant adding **other order lines**
   (`OL000085`, `OL000183`) — valid, resolvable citations pointing at the
   wrong deal. Fixed by filtering to records naming this recommendation's own
   product, customer, or order line.
2. Its trigger metric (citation *density* — figures with their own record)
   cannot be moved by retrieval at all, because the gap is upstream: five of
   sixteen figures in a typical pack (`invoice_price`, `pocket_price`,
   `total_deductions`, `erosion_pct`, `deduction_count`) are subtotals Track A
   computed with no graph row behind them. A trigger its own remedy can't
   move fires forever and fixes nothing. Split into `citation_density`
   (diagnostic, reported) and `support_ratio` (records per figure — what
   retrieval *can* move — the actual trigger).

## Part 3 — Building D6

`src/evaluation/narrative_harness.py` + `evaluate_narratives.py`: a 24-case
frozen gold set (`data/narrative_gold_set.json`, v1.1, generated by
`scripts/build_narrative_gold_set.py`) whose expected values are read straight
off disk and **never** through `build_facts()` — the code under test. A drift
guard (`NarrativeEvaluationReport.trustworthy`) refuses to write a report if
the gold set and the fact pack disagree about a recommendation; verified
end-to-end (corrupted a gold value, confirmed exit code 2, confirmed no
report file was written).

The gold set started at 12 cases. At that size, one wrong answer moves the
served-wrong rate by 8 percentage points — too coarse to compare against a 5%
target — so it was doubled to 24, spread evenly across the three distinct
waterfall shapes present in the graph (8 cases each at 2, 3, and 4 deduction
steps).

## Part 4 — The defects found while measuring, in the order they surfaced

This is the part of the session that took the most time, and it's the part
worth being explicit about: **five of the defects below were in the
measurement itself, not in the narrative system**, and each one moved the
reported numbers in a way that happened to look better or worse than reality.
Each was found by reading the actual flagged narrative text, not by trusting
a rate.

### 1. The D4-vs-D5 comparison was invalid

`--no-reliability` (meant to reproduce plain D4 behaviour: one sample, no
agreement test) still ran D5's attribution gate underneath. Both
configurations filtered misattributions and both scored 0.0% served-wrong,
making the entire reliability layer look pointless by construction — the
instrument couldn't tell the two apart. Fixed by making attribution
enforcement a separate policy (`RELIABILITY_ENFORCE_ATTRIBUTION`): always
*measured*, optionally *enforced*.

### 2. `served_wrong` conflated two different failures

Auditing the first honest baseline run, two narratives were flagged as
"wrong" while stating **every figure correctly**. What they'd actually done
was cite one record (the order line) after all four claims — a genuine
defect, since the order line doesn't contain the freight figure a reader
would want to check, but not the same event as asserting a false number.
Merging the two into one metric meant the baseline's error rate was partly
manufactured — and it inflated the baseline in a way that flattered D5,
which is exactly the kind of unsupported framing this track exists to
prevent. Split into `served_wrong` (false content) and `weak_citation`
(correct, but under-cited), reported separately.

### 3. Attribution false positive: range endpoints

*"Total erosion **from the** list price **to the** pocket price is
6,886.88 SAR"* — both ends of a range are being *named*, not each given a
value. `from the` was already treated as a non-assertion; `to the` was not,
so the pocket price read as a bare (and wrong) assertion. This single bug had
been inflating every served-wrong measurement taken before it was caught —
including a 13.0% baseline figure from earlier in the session that turned out
to be substantially this bug, not model error.

### 4. Attribution false positive: comparatives

*"...with the final pocket price **being 44.33 SAR lower than** the invoice
price"* is correct English and a **true** statement (2,484.50 − 2,440.17 =
44.33) — the figure is the *gap*, not the pocket price's value. Comparative
constructions following a role are now exempted.

### 5. Attribution false positive: terminal reference (the one that generalised the fix)

*"...results in the final pocket price [OrderLine:OL000012]"* — the role is
named as an outcome with no number following it at all; the actual value had
already been stated in the previous sentence. This produced the underlying
rule that subsumes most of the earlier patches: **English states an asserted
value *after* its noun.** A role with nothing quantitative following it is
being referred to, not valued. Added as the first gate a role must pass
before any of the other exemption logic runs.

### A sixth defect, mechanical rather than linguistic

While adding the comparative-exemption pattern, a shell heredoc silently
turned an intended `\b` (regex word boundary) into a **literal backspace
character** inside the compiled pattern. The source code still *looked*
correct; the pattern simply matched nothing, and the exemption it was meant
to add did nothing. Caught only by testing the exemption directly and getting
an unexpected "still flagged" result. A regression test now asserts no
compiled pattern in the module contains a control character, and a repo-wide
scan confirmed no other file was affected.

### And one in the narrative generator itself, not the checker

The prompt's own worked example — meant to teach citation density — repeated
one citation handle (`PriceComponent:PC0000000`) across all three of its
example sentences. The model learned exactly that habit, which is what the
weak-citation metric (defect #2) then correctly caught in real output. Fixed
by making the example demonstrate a **distinct** record per figure. Measured
effect: weak-citation rate dropped from 4.2% to 0.0%, and answer relevance
rose from 0.927 to 1.000.

## The D4-vs-D5 comparison, finally done right

Both configurations were re-run with the *identical, final* checker code.
Confirmed by file timestamp, not assumed: every source file the comparison
touches (`attribution.py`, `consistency.py`, `corrective.py`, `narrator.py`,
`narrative_harness.py`, `generator.py`, `settings.py`,
`evaluate_narratives.py`) predates both report files. Same 24-case gold set,
same model (`qwen2.5:7b`), same payloads, same temperature. They differ only
in `RELIABILITY_SAMPLES`, `RELIABILITY_MIN_AGREEMENT`, and
`RELIABILITY_ENFORCE_ATTRIBUTION`.

| Configuration | Served | Served-wrong | Agreement |
|---|---|---|---|
| D4 baseline (k=1, gate off) | 96% (23/24) | **0.0%** | 1.000 (trivial — one sample) |
| D5 (k=3, gate on) | 100% (24/24) | **0.0%** | 0.907 (real cross-sample agreement) |

**Neither configuration produced a served-wrong answer on this run**, and that
is reported as-is rather than reframed. With the checker corrected,
`qwen2.5:7b` did not misattribute a role in either 24-case pass on this
occasion. Claiming a served-wrong *reduction* this run does not show would
repeat the exact mistake this session spent most of its time correcting.

What D5 did change: it recovered `NAR-0020`, which the baseline abstained on
— that case's one k=1 sample failed a check, and k=1 has no fallback; D5's
three samples gave it enough to reach quorum and agreement instead. Service
rate: 96% → 100%.

The claim this session can support **without qualification** is the
deterministic one, not the sampled one: given one verification-clean but
misattributed narrative, constructed as a test fixture
(`test_the_attribution_gate_is_what_separates_d5_from_d4`), the D4-equivalent
configuration serves it (100% served-wrong on that single case) and D5
withholds it (0%), every time, by construction. Full detail and the honest
reading of both results:
[docs/D5_D6_reliability_and_evaluation.md, §5](docs/D5_D6_reliability_and_evaluation.md#5-results).
